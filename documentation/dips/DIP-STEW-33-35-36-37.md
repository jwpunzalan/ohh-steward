### Revision Note

This is not a refresh of a stale draft — no prior DIP exists for these four tickets. It is included here because each item was independently verified against the live `ohhsteward-dev` schema and the current `dev` branch before drafting (per the Grounding Check below), and two items turned out to have a narrower scope than their ticket text implies:

1. **STEW-33's scope is 3 functions, not 4.** The original ticket names `rpc_bootstrap_household`, `rpc_create_budget`, `is_household_parent`, `can_access_budget`. Live query against `ohhsteward-dev` confirms `rpc_bootstrap_household()` already has zero `anon`/`authenticated` grants (only `postgres`/`service_role`) — already closed, apparently as a side effect of Story 1.1.G2 moving bootstrap to a database trigger and making the RPC client-uncallable. Only `rpc_create_budget(text, text, uuid[])`, `is_household_parent(uuid)`, and `can_access_budget(uuid)` still grant `EXECUTE` to `anon` live. This DIP revokes those three only; touching `rpc_bootstrap_household` would be a no-op change to a function that's arguably a candidate for outright removal in a future cleanup, not this DIP's concern.
2. **STEW-35 is defense-in-depth, not an open external-facing leak.** Reading `supabase/functions/accept-invite/index.ts` confirms it already treats *any* error from `rpc_accept_invite` as a uniform generic 400 (`"invalid or expired invite"`) — the raw Postgres `unique_violation` text is not actually reaching an HTTP client today through the one path that calls this RPC. The fix is still warranted: `rpc_accept_invite` itself is the authoritative boundary and should not depend on its one current caller's blanket catch-all as the only thing standing between a constraint violation and a raw error — Secure Coding obligation 10 is about the function's own behavior, not just what happens to be true of today's single caller. Framed honestly as hardening, not as closing an active leak.
3. **STEW-37 is mobile-only.** Web has no client-side idle-timer at all — grep of `apps/web` confirms it. Story 1.4's own DoD requires idle-timeout to be enforced *server-side* (JWT expiry) independent of client-side timers; web's enforcement is already server-side by design and untouched by this gap. STEW-37's "not enforced before every action" defect is specific to mobile's `AsyncStorage`-backed idle timer, which today is only consulted at cold-start and on an `AppState` foreground transition — not before the six protected mutating actions that exist today.
4. **STEW-36 spans 4 handlers, not 2.** Both platforms have a `handleSubmit` (signup/signin) and a separate `handleVerifyMfa` (2FA code entry) — all four have the identical gap (no `try/catch`), confirmed by reading each in full.

### Acceptance Criteria

1. **(STEW-33)** Given `rpc_create_budget(text, text, uuid[])`, `is_household_parent(uuid)`, and `can_access_budget(uuid)`, when their live `EXECUTE` grants are queried after this migration, then `anon` holds no grant on any of the three, and `authenticated`'s existing grant on each is unchanged.
2. **(STEW-33, negative security)** Given an unauthenticated (`anon`) client, when it calls any of the three RPCs directly (not just through another function that happens to call them internally), then PostgREST rejects the call at the grant layer with a permission error — the call never reaches each function's internal `auth.uid()` check.
3. **(STEW-35)** Given `rpc_accept_invite`'s `household_member` insert raises `unique_violation` for any reason, when that occurs, then the function raises the same generic `'invalid or expired invite'` exception already used for every other invite-rejection branch, and the invite's `status` remains `'pending'` — never marked `'accepted'` on a failed insert.
4. **(STEW-36)** Given the web or mobile sign-up, sign-in, or MFA-verify handler, when any call inside it throws instead of returning a normal `{ data, error }` result (a network exception, a client-construction failure), then the handler catches it, shows a generic user-facing message, and resets `submitting` to `false` — the form remains usable without a page reload or app restart.
5. **(STEW-37)** Given a mobile session idle (no protected action taken) for longer than the household's configured `session_timeout_minutes`, when the user attempts any of the six protected actions (create Budget, create Account, create Transaction, set Splits, send Invite, delete Account), then the action is blocked before any network call, the local session is signed out (`scope: 'local'`, matching the existing pattern — never the `'global'` scope), and the screen returns to the auth flow.
6. **(STEW-37, regression guard)** Given the same idle-elapsed check when idle time has *not* elapsed, then the action proceeds exactly as it does today, and `touchActivity()` still records the new activity timestamp — no change to today's behavior for the common case.

### Code Requirements

**Secure Coding Requirements** (verbatim, per §6 of the Atlas Core system prompt):

1. **Injection.** All SQL is parameterized. String concatenation or interpolation of any value into SQL, shell commands, file paths, or query strings is prohibited. This applies equally to SQL written by Atlas — any SQL supplied in a DIP must itself be parameterized, or explicitly marked as a one-time DDL/migration statement executed with no user-supplied input. (CWE-89, CWE-78; ASVS V5)
2. **Input validation at trust boundaries.** Validate type, range, length, format, and allowed values on every input crossing a boundary — API route, RPC call, Edge Function, file upload, or external system response. Validate server-side; client-side validation is never sufficient. Reject by default rather than sanitize where a closed set of valid values exists. (ASVS V5)
3. **Output encoding.** Encode data for the context it enters — HTML, URL, SQL identifier, log line, or downstream message/notification. (CWE-79; ASVS V5)
4. **Secrets.** No credential, connection string, key, token, or certificate may appear in source, configuration committed to the repository, test fixtures, log output, error messages, or telemetry. 7. **Least privilege.** Database roles, RLS policies, service credentials, and API scopes are the minimum required by the story. Do not grant broad access for convenience. (ASVS V1)

9. **Deserialization and parsing.** Treat every inbound payload as untrusted — request bodies, webhook payloads, file uploads. Do not deserialize to arbitrary or polymorphic types from untrusted input; validate against an explicit schema rather than trusting shape. (CWE-502, CWE-611; ASVS V5)

**Migration — `supabase/migrations/<timestamp>_hardening_batch_stew33_35.sql`:**

```sql
-- STEW-33 — explicit anon-revoke retrofit on 3 of the 4 originally-named
-- functions (rpc_bootstrap_household already has zero anon/authenticated
-- grants live — confirmed this session, excluded here, not touched).
revoke execute on function public.rpc_create_budget(text, text, uuid[]) from anon;
revoke execute on function public.is_household_parent(uuid) from anon;
revoke execute on function public.can_access_budget(uuid) from anon;

-- STEW-35 — rpc_accept_invite hardening. Same signature as the live
-- function (uuid, text, uuid) -- CREATE OR REPLACE is safe here, no
-- PostgREST overload hazard, and grants (service_role-only) are preserved
-- automatically by REPLACE (unlike a DROP+CREATE, which would require
-- re-granting). Only the household_member insert gains a nested exception
-- block; every other line is byte-identical to the live body.
create or replace function public.rpc_accept_invite(p_token uuid, p_email text, p_auth_user_id uuid)
returns void
security definer
set search_path = public
language plpgsql
as $$
declare
  v_invite record;
begin
  select * into v_invite
    from invite
   where token = p_token
   for update;

  if v_invite is null
     or v_invite.status <> 'pending'
     or v_invite.expires_at <= now()
     or v_invite.email <> p_email then
    raise exception 'invalid or expired invite';
  end if;

  -- STEW-35: the RPC itself is the authoritative boundary for this
  -- constraint, independent of what its current one caller (the
  -- accept-invite Edge Function) happens to already catch generically.
  begin
    insert into household_member (household_id, auth_user_id, role)
    values (v_invite.household_id, p_auth_user_id, v_invite.role);
  exception
    when unique_violation then
      raise exception 'invalid or expired invite';
  end;

  update invite set status = 'accepted' where id = v_invite.id;
end;
$$;
```

export async function guardIdleOrSignOut(
  sessionTimeoutMinutes: number,
): Promise<boolean> {
  const idleElapsedMinutes = await getIdleElapsedMinutes();
  if (idleElapsedMinutes > sessionTimeoutMinutes) {
    // Same fail-closed, local-scope-only pattern as
    // resumeStoredSessionIfAllowed / checkIdleAndSignOutIfElapsed above —
    // never signs the user out of other devices.

    await clearStoredSession();
    return false;
  }
  await touchActivity();
  return true;
}
